## 0. 先说结论

| 项 | 内容 |
|---|---|
| 它是什么 | Windows 上的多显示器壁纸轮播器：把本地图片目录按固定间隔轮流设成桌面壁纸，每块屏可各播各的 |
| 技术栈 | Electron 44 + 原生 HTML/CSS/JS（**无框架、无打包器**，renderer 直接是三个文件）+ `koffi` 直调 Win32 COM |
| 运行时依赖 | 只有两个：`koffi`（FFI，调 `IDesktopWallpaper` COM / user32 / advapi32）、`exifr`（EXIF 读取） |
| 代码规模 | 主进程约 7.0k 行（main 1787 + scheduler 1140 + fileActions 582 + store 537 + clipboardWin 326 …），渲染层约 4.3k 行（app.js 2843 + html 440 + css 1045） |
| 当前状态 | 第 37 轮收尾，功能完整可用（含动态桌面/视频壁纸/视频转码优化）；**CHANGELOG 停在第二十五轮**，第 26 轮起的逐轮记录只有 git log（本文件第 11 节有摘要）；打包产物落后于代码 |
| 要不要接手 Windows Only | 是。逐屏壁纸依赖 COM 接口，代码里没有为跨平台留抽象，别想着移植 |

**最容易踩的三件事**（详见第 5 节）：别按进程名杀 `electron.exe` —— 而且**按项目目录过滤也不够**：同一项目的调试实例和你正在用的实例共用同一个 exe 路径，只能按 PID 关树；调试实例必须用隔离的 `--user-data-dir`（用户的应用常年开着，共用 profile 会让第二个实例**卡在 Chromium 启动阶段、一行日志都没有**）；改 `config:set` 会触发整轮频道重建，纯界面状态要另开短路。

**排查「Electron 起不来」的第 0 步**：先确认环境里没有 `ELECTRON_RUN_AS_NODE`（存在即致命，值是什么都不重要）。有它的话 Electron 退化成纯 Node，`app` / `clipboard` 全是 `undefined`，报出来的错和你的代码毫无关系。直接用 `python tools/run-electron.py <脚本>` 可以一次性绕开这一条和 profile 锁。

## 1. 十分钟跑起来

```bash
git clone https://gitee.com/klanf/per-monitor-wallpaper.git
cd per-monitor-wallpaper
npm install          # 会拉 Electron（数百 MB）；建议把 npm/Electron 缓存指到 D 盘
npm run fixtures     # 生成测试图：120 张渐变 PNG + 纯色 BMP（不进版本库，每次克隆都要跑）
npm start
```

首次启动建议先用 `tools/fixtures/` 里的测试目录，**别直接指向真实图库**（三万张图的第一次扫描和缩略图生成要跑一会儿）。

| 命令 | 作用 | 需要 Electron 跑起来吗 |
|---|---|---|
| `npm start` | 正常启动 | — |
| `npm run start:debug` | 带 CDP 端口 9222 启动（所有 `verify:*` 端到端脚本的前提） | — |
| `npm run verify:unit` | 调度器与配置单测（153 项） | **不需要** |
| `npm run verify:wiring` | 渲染层静态接线检查（37 项） | **不需要** |
| `npm run verify:resume` | 「重启后接着上次那张播」单测（28 项，写入函数是替身，不碰桌面） | **不需要** |
| `npm run verify:clipboard` | 「复制图像到剪贴板」两条路（44 项，用真剪贴板，**跑完自动还原剪贴板**） | 需要（走 `run-electron.py` 自动隔离） |
| `npm run status` / `npm run wallpaper:now` | 看每块屏现在挂着什么（后者直接问系统，不看应用状态） | 不需要（后者） |
| `npm run app:eval -- "<表达式>"` | 在运行中的应用里求值（`wp` 已注入） | 需要 |
| `npm run verify:e2e` / `:features` / `:fixes` / `:ui` / `:order` / `:cycle` / `:tray` | 端到端断言（CDP 驱动界面 + 系统侧回读） | **需要** |
| `npm run dist` 或 `打包exe.bat` | 出安装包 / 免安装版 | 不需要 |

需要反复重启应用时，用 `python tools/launch-dev.py`（可加 `--cdp` / `--hidden`）。它替你做三件直接从 shell 起 Electron 会出事的操作：清掉环境注入的 `ELECTRON_RUN_AS_NODE`（留着会让 Electron 退化成纯 Node 然后崩）、让进程脱离父进程组、把输出重定向到日志文件（用管道而不读会把进程吊死）。

要**前台跑完一个 Electron 脚本并拿退出码**（例如 `verify:clipboard`），用 `python tools/run-electron.py <脚本>`。它和 `launch-dev.py` 分工不重叠：后者解决「怎么让应用活下去」，它解决「怎么让脚本在有应用正在跑的情况下还能跑起来」—— 它会额外给一个**一次性的隔离 `user-data-dir`**，否则第二个实例会在 Chromium 启动阶段被 profile 单例锁挡住。`npm run verify:clipboard` 已经走它。

## 2. 代码地图

```
主进程（Node，持有全部状态与调度权）
  main.js              窗口 / 菜单 / IPC 总装配 / 热键 / 桌面右键菜单  1763 行
  scheduler.js         多频道轮播调度器（每屏一路，各自定时器）        1140 行
  store.js             配置：默认值 + 收紧 + 原子写 + 每屏覆盖         537 行
  playbackState.js     播放进度存档（playback.json）                   132 行
  scanner.js           目录遍历 + Collator 自然排序                     84 行
  desktopWallpaper.js  IDesktopWallpaper COM 手工 vtable 分发          398 行
  win32.js             壁纸写入：优先 COM，SPI 仅兜底                  259 行
  shellMenu.js         桌面右键菜单（写 HKCU 注册表）                  320 行
  tray.js              托盘图标 / 菜单 / 开机自启                      318 行
  thumbnails.js        缩略图生成 + wpthumb:// 协议 + 磁盘缓存         323 行
  fileActions.js       复制 / 移动 / 删除 / 外部打开 / 打开方式        463 行
  clipboardWin.js      koffi 直写 CF_HDROP / CF_DIBV5 + 剪贴板回读     326 行
  exif.js / imageSize.js  EXIF 分组可读化 / 只读文件头拿分辨率
  preload.js           contextIsolation 下的白名单桥                   184 行

渲染进程（纯前端，不持有状态，被 tick 推着走）
  renderer/index.html  双图层舞台 + HUD + 胶片条 + 三个面板           440 行
  renderer/app.js      预览器 + 面板交互（最大的一个文件）            2843 行
  renderer/style.css   只动 transform / opacity 的动画                1045 行
```

**数据流（记住这一条，代码就顺了）：**

```
[主进程] scheduler 每推进一步 → 写系统壁纸 + 广播 channel:tick
                                     │
                                     ▼
[渲染进程] app.js 收到 tick → 画过渡动画 + 更新 HUD / 胶片条 / 计数
        渲染层从不自己数秒、不自己决定下一张是什么
        用户改配置 → preload → main 的 config:set → applyConfigChange → scheduler.rebuild
```

反向通道只有两条值得一提：全局热键（主进程知道该动哪块屏，通过 `preview:select` 让界面跟过去）和 `files:changed`（文件被移动/删除后通知界面重画）。

## 3. 概念词典（这套词是本项目自造的，先对齐）

| 词 | 含义 |
|---|---|
| **频道 channel** | 一路独立轮播。统一模式 1 路（id 为 `UNIFIED_ID`）；每屏模式每台显示器 1 路（id 是该显示器的设备路径） |
| **profile** | 某个频道实际生效的配置 = 顶层配置 `deepMerge` `monitors[id]`。只有 `PROFILE_KEYS` 这 13 个键允许被每屏覆盖：`albumId / recursive / interval / animation / duration / shuffle / fit / skipSizeTwin` + 动态桌面新增的 `kenBurns / fpsCap / videoPlayFull / breath / timeOfDay` |
| **相簿 album** | `{ id, name, folders: [{ path, enabled }] }`。**目录在数组里的顺序就是播放顺序**。旧配置里的单个目录会自动包装成同名相簿（`migrateLegacyFolders`） |
| **`resolveProfile()`** | 派生出只读的 `folder` 字段给老代码/老断言用。**新代码一律读 `albumId`，不要写 `folder`** |
| **tick** | 主进程推进一帧后广播的事件，是渲染层唯一的画面驱动源 |
| **previewId** | 当前预览的那一路。全局热键作用在它上面，窗口藏在托盘里时也是 |
| **`_orderFor` / `orders`** | 随机模式洗出来的播放顺序表。`rescan()` 会清掉它（重洗）；`autoScan()` 故意不清（不洗牌） |
| **scanCache** | 目录扫描缓存，键是 `${目录}::${是否递归}`。外部往目录里加图程序是不知道的，只能靠清它触发真扫 |
| **`unified-only` / `per-monitor-only`** | HTML 上的 class，由 `body.mode-per-monitor` 配合 CSS 决定显示。改设置项位置时要尊重这套规则，别把统一项放进每屏可见区 |
| **延迟渲染（剪贴板）** | Chromium 写剪贴板时只是「认领」，真实字节等粘贴方来要的时候才生成。所以 `clipboard.write()` resolve **不等于**剪贴板里真有数据 —— 复制类操作一律以主进程 `clipboardWin.readImageStatus()` 的回读为准 |

## 4. 关键设计决定（改之前先知道为什么）

| 决定 | 为什么 |
|---|---|
| **调度权全在主进程** | 关掉窗口、藏在托盘里也要继续轮播。渲染层只负责画收到的那一帧 |
| **播放进度存 index，另外按相簿在 `playback.json` 里记 path** | 每次换图都要写（间隔可能只有几秒），塞进 `config.json` 会把配置文件当日志写；分开存，配置归配置 |
| **自动扫描只清 `scanCache`，不清 `orders`** | 手动「重新扫描」= 用户要重来一遍，会连顺序一起洗；自动扫描是后台静默发生的，把正在看的顺序搅乱只会让人莫名其妙。副作用：新图接在列表末尾、已删的图消失，顺序不变 |
| **自动扫描后按 path 找回当前帧** | 进度存的是序号，列表前面少一张图序号就整体前移 —— 实测播到第 2 张时第 1 张被删，画面凭空跳到第 3 张。所以扫完用 `findIndex(f => f.path === 原路径)` 复位（单测 §27 专门盯这条） |
| **定时器一律 `unref()`** | 进程存活不该由定时器决定（存活靠窗口/托盘）。不 unref 的话单测跑完进程不退出 |
| **自动扫描定时器挂在 `_rebuild()` 末尾** | 改配置、切模式、插拔显示器、手动重扫最后都落到 rebuild，于是不管哪条路径改的间隔都立刻重新计时，不用每个调用点记得刷一次 |
| **缩略图走 `wpthumb://` 自定义协议，路径用 UTF-16LE + base64url 编码** | 一屏几十个 URL，每个都发一次 IPC 太浪费；Windows 中文路径很常见，用 UTF-8 会错位（和 `thumbnails.js` 的 `decodePath` 必须对应） |
| **删除只有一份实现（主进程 `trashWithPermission`）** | 右键菜单、胶片条垃圾桶、托盘、热键四个入口共用。永远只进回收站，不提供永久删除 |
| **桌面右键菜单写 HKCU** | 不需要管理员权限，卸载就是删掉那棵子树。Windows 11 下这两项在「显示更多选项」里 |
| **`contextIsolation: true` + preload 白名单** | 渲染层拿不到 Node。要加能力就在 `preload.js` 暴露一个方法 + `main.js` 里 `ipcMain.handle` |
| **`UI_ONLY_KEYS` 短路** | `config:set` 无条件 `scheduler.rebuild()`；纯界面状态（如记住设置面板停在哪个分类页）走同一条通道就会「点一下＝重扫一遍相簿」。patch 全是这些键时只写盘不重建 |
| **设置面板分类标签页** | 21 个字段块挤在一列里找开关要滚好几屏。非当前页整页 `hidden`（不只是 CSS 隐藏 —— 否则 Tab 键能聚焦进看不见的控件） |
| **复制图像三步走：硬超时 → 回读校验 → Win32 兜底** | Electron 44 的 `clipboard.write()` 在剪贴板被别的程序占着时可能**既不 resolve 也不 reject**，「点了没反应」就是这么来的。`fileActions.copyImage()` 现在自带 1500ms 死线，超时/报错都转 `clipboardWin.writeImage()` 直写 `CF_DIBV5`，写完再回读量体积 |
| **「打开方式」另起 `rundll32` 进程，不用 `SHOpenWithDialog`** | 后者是**模态**的，in-process 调用会把主进程消息循环卡到对话框关闭为止；而轮播定时器全在主进程里，卡住就是桌面定格 |
| **复制图像分两条路，阈值 12 MP**（`fileActions.FAST_PATH_PIXELS`） | 真正的成本不是「写剪贴板」，而是 `nativeImage.toPNG()` ——它**同步**执行，66.7 MP 一张要 **4887 ms**，期间主进程完全不刷新。而 Windows 程序读的是 `CF_DIB` / `CF_DIBV5`，那份 PNG 编码白烧。所以大图跳过编码直接拼 `CF_DIBV5`（同图 813 ms vs 6782 ms），小图保留注册格式 `PNG`（小图上 `toPNG` 只要几百毫秒，兼容性更划算）。阈值 12 MP 的依据：实测库存 p90 = 11.7 MP，九成图片行为不变 |
| **复制前先报进度（`copyImageWithNotice`）** | 同步冻结期间屏幕一个像素都不会变，用户看到的就是「点了没反应」。所以先用 `imageSize.readImageSize()` **只读文件头**算出尺寸，把提示交出去、**让出一帧（80 ms）**，再去做那段同步活。这条比快路更根本：它把「没反应」变成「在等」，且对任何尺寸都成立 |

## 5. 踩过的坑（改之前先看这张表）

| # | 症状 | 根因 | 解法 / 位置 |
|---|---|---|---|
| 1 | 跑一次自动化就把用户正在用的壁纸切换器关掉 | 本机同时有多个 Electron 应用，`electron.exe` 不专属本项目；`taskkill /IM electron.exe` 会误杀 | **禁止按进程名杀**。按镜像路径过滤（`OpenProcess` + `QueryFullProcessImageNameW`），取不到路径就跳过。现成工具：`vinyl-player/tools/proc-list.py`（`--under=<目录>` + `--kill`，缺 `--under` 时拒绝执行） |
| 2 | 调试实例静默秒退，什么输出都没有 | 单实例锁：`%APPDATA%\electron-wallpaper` | 起调试实例必须 `--user-data-dir=<隔离目录>`。注意 **Electron 的 appData 不吃 `APPDATA` 环境变量**（走 `SHGetKnownFolderPath`），只设环境变量没用 |
| 3 | Electron 在会话里根本起不来（连三行的最小 app 也 189ms 秒退） | **已定位，两个原因**：① 环境里被注入 `ELECTRON_RUN_AS_NODE`（存在即致命）→ Electron 退化成纯 Node，`app` 是 `undefined`，秒退；② 和正在运行的应用共用 `user-data-dir` → 卡在 Chromium 启动阶段（表现为卡住而非秒退）。都不是项目 bug | 先写最小 Electron app 做 A/B 再怀疑自己代码。用 `python tools/run-electron.py <脚本>` 一次绕开这两条。退路仍是：单测 + `npm run verify:wiring`，UI 观感交用户实测，**并在交付里如实标注「真机未做」** |
| 4 | 界面「时好时坏」：启动后头几秒停在「未选择相簿」占位 | 异步数据（相簿列表）就位晚于频道推送，而卡片是渲染频道时画的 | **异步数据加载完必须补渲染所有引用它的视图**（`refreshAlbums()` 末尾补 `renderCards()`）。别指望下一次推送自愈 |
| 5 | 用户说「重启了没看到这个新设置」 | 新设置项被长内容挡住了（全局项排在每屏显示器卡片之后） | 排查顺序：① 看用户真实 `config.json` 里**有没有新键**（有＝新代码在跑）② 再找位置/可见性问题。**全局设置一律排在每屏卡片之前** |
| 6 | 点一下界面小开关，磁盘就狂转 | `config:set` → `applyConfigChange` → `scheduler.rebuild()` | 纯界面配置键加进 `UI_ONLY_KEYS`（`src/main.js`） |
| 7 | 「点了没反应」，读代码看不出问题 | 搬 DOM 时把某个 id 搬丢了，`$('xxx')` 拿到 `null` | `npm run verify:wiring` 会核对 app.js 里**每一个** `$('id')` 在 HTML 里是否存在。这条当场抓到过 `.settings-body` 只有 class 没 id |
| 8 | 同一文件改两处，前一处的修改消失，两个工具都报成功 | 并行发出的多个 Edit 基于同一份旧快照，后者覆盖前者 | 改同一文件多处：**串行发**，或用一次性脚本（读全文 → 逐条 replace → 写回） |
| 9 | 从 Python 起 PowerShell 做环境验证，`Get-Command conda` 找不到；cmd 里却找得到 | 沙箱环境里没有 `PATHEXT`，PowerShell 退回自己的默认值 `.CPL`。**「cmd 能找到、PowerShell 找不到」这个矛盾组合就是它** | 传环境前把注册表的 `PATHEXT` 补回去；`PATH` 统一成一个键名（别同时有 `Path` 和 `PATH`） |
| 10 | push 后提示 `Everything up-to-date` / `upstream is gone` / `nothing to commit`，看着像失败 | 本地 remote-tracking 引用过期 | `git fetch origin` 后用 `git rev-parse HEAD origin/master` 复核。**别信那几行输出** |
| 11 | 文档说设置面板里有「还原壁纸」，界面里找不到 | **这个功能根本没做**（见第 9 节待办）。逐屏写入会把桌面切成「每屏图片」模式，顶掉系统幻灯片设置 | 已把文档改成实话（Windows「个性化 → 背景」重选）。要做真按钮是另一个工作项 |
| 12 | 自动化断言偶发失败 | 和真人共用窗口时，用户正在点 | 先多时间点探针证明稳定再下结论 |
| 13 | 右键「复制图像到剪贴板」**点了没有任何提示**、粘贴也是空的 | Electron 44 的 `clipboard.write()` 在剪贴板被占 / 内部状态没走完时既不 resolve 也不 reject，菜单 click 的 `await` 永远停住 | `fileActions.CLIPBOARD_WRITE_TIMEOUT_MS` 硬超时 → 转 `clipboardWin.writeImage()` 原生直写 → `readImageStatus()` 回读核体积。回归：`npm run verify:clipboard` |
| 14 | 自动化收尾时把**用户正在跑的实例**一起关了 | `proc-list.py --kill --under=<目录>` 按**镜像路径**过滤，而调试实例与用户实例共用同一个 `electron.exe` —— 路径只能区分「哪个项目」，区分不了「同一项目的哪个实例」 | 关自己起的实例必须**按 PID 关它那棵树**（先子后父）。`proc-list.py` 适合「看」，不适合「关同一个项目里的某一个」 |

## 6. 开发约定

- **改渲染层**（html / css / app.js）→ 改完跑 `npm run verify:wiring`。它会核对 id 引用、重复 id、设置面板四个标签页与内容页是否对得上。
- **加配置键** → `src/store.js` 的 `DEFAULTS` 加默认值 + `normalizeConfig` 里收紧（写个 `clampXxx`）。**纯界面状态还要加进 `src/main.js` 的 `UI_ONLY_KEYS`**。
- **允许每屏覆盖的键** → 加进 `PROFILE_KEYS`（`src/store.js`），否则写进 `monitors[id]` 也不会生效。
- **改调度逻辑** → 在 `tools/test-scheduler.js` 加断言。它注入的是假写入函数，**不会动真实桌面**，可以放开写。
- **调试实例** → 一律 `--user-data-dir` 隔离；收尾用 CDP `Browser.close`，关不掉就 `TaskStop` 当初启动它的后台任务（整树杀）。
- **改完要不要重启** → 主进程改动和渲染层改动都要重启应用才生效（没有热重载）。托盘新增项同理。
- **提交节奏** → 改完即 commit + push（Gitee `master`），并在 `CHANGELOG.md` 记一轮（「第 N 轮：现象 / 设计决定 / 改动 / 验证」是既有格式）。本项目**不递增版本号**（一直 0.1.0）。

## 11. 动态桌面纪元（2026-09-25 ~ 09-26，a3c8004 → 863f9c2）—— 给 zcode 的增量交接

这一节覆盖第二十五轮交接之后的所有工作：**把播放画面挂到真实桌面**（动态桌面舞台）、视频/网页壁纸、视频转码优化、以及一整串 Win11 桌面环境的硬骨头。前面 1~10 节讲过的不再重复，这里只讲增量。

### 11.1 它是什么、怎么挂上去的

- **统一配置同样生效**（52 轮：一块跨屏窗口盖住虚拟桌面并集，`src/stagePlan.js` 算并集；此前统一伪频道被 syncTo 跳过，统一模式下动态桌面整个不生效——用户实报后补上。52 轮追记：真机探针抓出 Electron Display 无顶层 width 的形状 bug——纯函数单测喂扁平假数据会掩盖它，跨「Electron 对象→纯函数」边界必须显式拍平）。
- **统一模式画面形态（53 轮）**：`liveStage.unifiedSplit`（默认 `span` 跨屏拼一幅；`per-display` = 每屏同一幅，用户最初预期的「每块屏各自显示同一张」）。展开逻辑在 `stagePlan.expandUnifiedChannel`（纯函数可单测）：伪频道 id 带 `::d<displayId>` 后缀防 stages Map 撞 key、`_displayId` 让 stageBounds 直达 Display（displayForMonitor 按尺寸匹配，同尺寸屏会撞车）、保留原 channelId 让 stage 渲染端 tick 过滤照常。UI 在设置→轮播→「动态桌面画面」（仅统一模式显示；53 轮追记：从系统页挪进轮播页，形态是统一配置自己的事）。探针 tools/tmp/probe-unified-split.js 双形态真机验证过。
- **「写入目标显示器」UI 已撤（53 轮追记，用户拍板「以舞台为主」）**：config `monitor` 键与后端 `resolveUnifiedTarget` 保留兼容（老配置的 primary/window/指定屏 仍生效），只是不再有设置入口——它只作用于系统壁纸层，动态桌面开着时画面全在舞台，入口留着只会让人以为能切舞台形态。
- **暂停时隐藏舞台（52 轮默认开 → 54 轮追记四默认关）**：`liveStage.hideOnPaused`，暂停时对该屏 `win.hide()`、恢复 `showInactive()`。起因是艾尔登法环独占全屏 × 舞台窗口的 4K flip 交换链 → 驱动挂死（6 次黑屏无信号、无 TDR/WHEA 日志，用户对照实验实锤：独占全屏+壁纸必炸、无边框+壁纸不炸）。跨屏统一舞台任一覆盖屏被暂停即藏。看门狗重挂会尊重 `rec.hiddenForPause`，不把隐藏态亮出来。**手动暂停（工具栏/托盘/热键）只冻结不藏窗**（53 轮）：manualPaused 集合按频道 id 记，用户只是要画面停、不是要让出桌面。**54 轮追记四改默认为关**：QQNT 截图/录屏遮罩（Electron 窗口，无 TOOLWINDOW、不 cloak）被 fullscreenWatch 误判全屏 → 舞台被藏（用户报「开截图舞台就掉，只有主屏掉」）；且用户不想要任何全屏的「掉/恢复」过程。现在全屏暂停=冻结不藏窗（停倒计时+停粒子，画面钉住），`hideOnPaused === true` 才藏——**玩独占全屏游戏（法环）前必须在设置里勾回**；已落盘的旧配置 `true` 不会被新默认覆盖，要手动去勾。QQ 本身则按进程镜像名直接排除出全屏判定（`fullscreenWatch.EXCLUDED_IMAGE_NAMES={'qq.exe'}`，只对盖住工作区的 eligible 窗口解析路径，取不到不排除）。
- **桌面手势切壁纸（54 轮追记五）**：`src/swipeWatch.js`，16ms 轮询 GetAsyncKeyState(VK_LBUTTON)+GetCursorPos+WindowFromPoint，**不用低级鼠标钩子**（消息泵卡顿风险不对称，事件一个不吞所以框选/拖图标不受输入层影响）。判定：起手点根窗口类 ∈ {Progman, WorkerW}（GA_ROOT 上溯，图标层是 Progman 子树；舞台 WS_EX_TRANSPARENT 穿透）+ 松手 |dx|≥120 且 |dx|≥4|dy|；左扫 next 右扫 prev；一次按压最多一触发 + 600ms 冷却。分发复用 main.js 的 `stepWallpaperAt(pt, dir)`（从 channelAtCursor 抽出的共用链路）。已知取舍：横向橡皮筋框选、横向拖图标同形会误触发——设置 `swipeSwitch`（默认开）可关。单测 `tools/test-swipe-watch.js`；koffi 的 `WindowFromPoint` 要 POINT **按值传**（`func('void *WindowFromPoint(Pt pt)')`，实测可用）。
- **粒子绕开鼠标（54 轮追记六）**：舞台窗口点击穿透收不到 mousemove，光标由 **liveStage 30Hz 轮询**（`screen.getCursorScreenPoint()` → 各舞台 `getContentBounds()` DIP 减法 = 本屏 CSS px，Electron 里 1 CSS px = 1 DIP 不用除缩放）→ `stage:cursor` 广播，窗外发 `null`。渲染端 `stage.js` 按开关 `particleCursor`（顶层键，默认开，PROFILE_KEYS 流进各屏）转发给粒子层；斥力 = 纯函数 `WPParticles.applyCursorAvoidance`：R=140px 内按 (1-d/R) 线性衰减外推位置（圆心 260px/s），**不改速度字段**（暂停恢复不跳），烟花三态（wait/rocket/burst）免疫。探针 `probe-cursor-feed`；单测 test-particles §7。
- **blur-dissolve 移出 random 随机池（54 轮追记七）**：用户报「切图有时候很模糊」——不是图坏，是 random（11 选 1，duration 1500ms）抽中 blur-dissolve：入场 `blur(24px)` 渐清晰，4K 图上 GPU 模糊慢，整个过渡期都是糊图。两端（app.js 预览层 / stage.js RANDOM_POOL）同步移出；**显式选仍可用**。顺带修：app.js 过渡收尾定时器只重置出场层，blur-dissolve 终态 `blur(0px)` 永久挂在活跃层上（filter 非 none = 巨图常驻一块合成层）——现在活跃层也清 filter/clip（不动 opacity/transform/zIndex）。
- **过渡动画不吃 fpsCap 闸门（54 轮追记八）**：用户报「切换动画生硬掉帧」——`fpsCap`（默认 30，用户配置也是 30）的 rAF 时间闸门把**整条渲染循环**闸在 30fps，过渡动画也在内。修法：`ensureRaf` 里 `animTick` 提出闸门每帧执行（跟满垂直同步），Ken Burns/呼吸/粒子/视频等**长驻**动画继续走闸门省电——闸门的存在意义（静止时 GPU 零占用）不受影响。已落盘的 `fpsCap: 30` 无需改。

- **首帧门控 + 透明窗口 + 缩略图快亮（53 轮引入 / 54 轮三连修）**：createStage 挂载后窗口保持隐藏，等渲染端把第一帧画上屏（stage.js 的 `stageFirstFrame` → main → `liveStage.onFirstFrame` 按 `e.sender` 对号）再 `showInactive`。54 轮起：① 超时（30s）**只告警不亮窗**（53 轮的 3s 兜底会亮纯黑窗，是黑闪复报的根因）；② 窗口本体 `transparent: true` + body 透明——任何空窗透出的是系统壁纸，物理上不可能露黑；③ 首帧先用 `wpthumb://` 磁盘缩略图（~6ms）垫帧点亮、原图解码完无缝重绘——等首帧从秒级压到亚秒级（探针实测 0.7s，原图被 6s 延迟流压住也不影响）。网页壁纸首帧等 iframe load（10s 兜底）。胶片条缩略图加载中显示微光占位（shimmer）+ 淡入。回归探针：`python tools/run-electron.py tools/tmp/probe-firstframe-noblack.js`（核心不变式「亮窗必有内容」+ 底色透明断言 + 页内 wpthumb fetch 诊断）。⚠️ 透明会改变交换链 alpha 路径，独占全屏游戏（艾尔登法环场景）如有异常，回退 liveStage.js 的 `transparent: true` 一行即可。
- **不是 WorkerW 子窗口方案**：本机 Win11 25H2 上 `SHELLDLL_DefView` 是自绘不透明的，挂它后面被永久盖住；`0x052C` 分裂在本机也不生成 WorkerW（参考项目 zm-main 的挂法在这台机器上不成立）。所以走 **HWND_TOP 置顶 + 越界裁剪**（OVERSCAN=2px 区域 clip）。
- 排错时抓过实锤：挂载后屏幕比对的像素证据、`capturePage` 假绿不可信、判活只信两次真实抓屏比像素。

### 11.6 视频转码优化（videoOptimize）要点

- 依据：GPU Engine 计数器实测双屏视频壁纸 VideoDecode=45.6%；解码开销 ∝ 宽×高×fps，库内约半数视频 60fps，60→30 是最大杠杆（预期减半）。
- **遇到才转**：wpimg 服务视频前调 `resolveForPlayback`，首播未命中且候选（fps≥31 且码率≥1500kbps）→ 后台串行队列转码，本次照播原件，下个循环起播副本。不是播放时实时转码（那是反模式）。
- **源库只读镜像**：源在 Syncthing 同步目录，绝不原地替换（会全量重同步）；副本按 `sha1(路径|大小|mtime)` 落 `D:/video-optimize-cache`；源删除/指纹失效 → 启动 10 分钟后清理扫描联动回收；40GB LRU。
- 实测：1:40 @1440×2560 60→30 用时 12.25s（8.4× 实时），CPU 0.045s，体积 ±3%。ffmpeg 是静态 v7.1（imageio-ffmpeg 提取），带 h264_nvenc，自动探测失败回退 libx264。
