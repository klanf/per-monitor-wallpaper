## 2. 复盘：按返工代价排序的盲区

### 2.1 【致命 · 会静默失效】「找没有 SHELLDLL_DefView 的 WorkerW」这条流行规则，在这台机器上会挑错

实测：现在有 **14 个** 顶层 WorkerW，**全都没有** `SHELLDLL_DefView` 子窗口，全是 202×56、不可见。
若照搬流行写法（`EnumWindows` → 找类名 WorkerW 且无 DefView → `SetParent` 过去），
**会挂到一个 202×56 的隐形小窗上** —— 结果：屏幕上什么都不出现，`SetParent` 还返回成功，**代码不报任何错**。

同时 **Progman 目前直接持有 SHELLDLL_DefView**，说明**还没有可用的挂载层**，必须先发 `0x052C` 让 Explorer 造一个。

⇒ **判定规则必须收紧成四条同时成立**（写进 `desktopHost.findWallpaperWorkerW()`）：

| # | 判据 | 为什么 |
|---|---|---|
| 1 | **在发完 `0x052C` 之后才出现**（发之前先快照句柄集合，取差集） | 排除那 14 个既存的隐形小窗 |
| 2 | 尺寸 ≈ 虚拟桌面（允许 ±8px 容差），**不接受 202×56 这种** | 同上 |
| 3 | `IsWindowVisible === true` | 同上 |
| 4 | `GetWindowThreadProcessId` == explorer.exe 的 pid | 排除别的进程（10676/11292）造的 WorkerW |

**并且：四条都不满足时必须"报错 + 退回静态壁纸"，绝不将就挂上去。**

### 2.2 【高 · 会崩】双图层交叉淡入 × 原图 = 内存/显存炸弹

现在渲染层**根本不加载原图**（`renderer/app.js:15`，只吃 256px 缩略图）。
改成原图后 Chromium 按**原始像素**解码：一张 7680×4320 的图 = **≈132 MB**；双图层交叉淡入要**同时**持有两张 ⇒ **峰值 260 MB+**，而屏幕只有 4K，根本用不着。

⇒ 必须 `createImageBitmap(blob, { resizeWidth, resizeHeight, resizeQuality:'high' })` **降采样到显示器物理尺寸**，画完 **必须 `.close()`**（不 close = GPU 显存泄漏，长跑必崩）。

### 2.3 【高 · 观感怪】`contain` 适配时四周露出的会是"被填充裁切过的另一张"

实测系统壁纸 `WallpaperStyle = 10`（填充）。若动态桌面用 `contain`，四周露出的就是系统壁纸那张**被填充裁切**的同一张图 —— 同一张图两种裁切叠在一起。
⇒ 需你定（见 §5 问题 2）。

### 2.4 【中 · 会被自己算错】显示器定位不要自己算，走现成映射

`monitors` 的键是 **IDesktopWallpaper 设备路径**，**不是** Electron 的 `display.id`（`src/main.js:59` 已明令禁止混用）。
项目已有 `desktopWallpaper.listMonitors()` 能给出 **devicePath → 物理矩形** 的映射（`desktopWallpaper.js:203-219`）⇒ stage 窗口定位一律走它。

⚠️ 另：副屏 1600 ÷ 1.5 = **1066.67 DIP（非整数）**，而 Electron `setBounds` 吃整数 DIP ⇒ 副屏窗口宽度会差 **1 物理像素**。断言里必须允许 ±1px，否则会被当成 bug 排查半天。

### 2.5 【中 · 长跑必崩/写 C 盘】原图协议不能沿用缩略图的缓存策略

`thumbnails.js:302` 现在给的是 `cache-control: public, max-age=600`。
原图协议若照抄，Chromium 会把几十 MB 的图**写进 `%APPDATA%\electron-wallpaper\Cache`（C 盘）**。
⇒ 原图协议必须 **`cache-control: no-store`**（用户明确在意 C 盘写入 / SSD 寿命）。

### 2.6 【中 · 看得见的灾难】Explorer 重启后窗口变孤儿 = 盖住图标

孤儿窗口不再是 desktop 的子窗口，会变成**普通顶层窗口**：浮在图标上面、Alt+Tab 里没有、看不出怎么关。用户会以为电脑坏了。
⇒ **看门狗必须放进阶段 1（不能等阶段 3）**，且孤儿时的动作是**先隐藏、再重挂**，不是直接重挂。

### 2.7 【中 · 一启动就踹人】`show()` 会抢焦点

⇒ stage 窗口必须：`showInactive()` 而非 `show()`、`focusable:false`、`skipTaskbar:true`、`frame:false`，并在原生侧补 `WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW`。

### 2.8 【中 · 影响渲染层写法，现在定比写完再改便宜】"默认 30fps"对纯 CSS 动画无效

纯 CSS 动画跑在合成器里，`requestAnimationFrame` 节流**管不到它**。
⇒ 想让帧率上限真的生效，**过渡与 Ken Burns 必须由渲染层自己的 tick 驱动（JS 驱动）**，不能用 CSS `animation`。
这是渲染层的架构性选择 —— 现在定下来，避免写完再推倒。

### 2.9 【低 · 语义要补】unified 模式 + `monitor='primary'/'window'` 在动态桌面下会破

非目标屏显示什么？需要一个明确语义（默认拟：**那些 stage 保持最后一帧冻结**）。已在 §5 说明，可不阻塞开工。

### 2.10 【低 · 防假绿】验证判据

`capturePage` / 截图是**从渲染进程取像**：窗口在屏幕上没刷新，也照样能取到画面 ⇒ **会给出假绿**。
⇒ 唯一可信判据 = **对 stage 窗口区域两次 `BitBlt` 抓屏比像素**，且两次采样要跨过一次换图。
项目已有 `tools/imgcodec.js`、`tools/clipboardReader.js` 的原生像素底子，可复用。

### 2.11 【低 · 待实测】cross-process `SetParent` 的输入链风险

把我们的窗口挂进 explorer 的窗口树，两个进程的窗口进了同一条输入链 —— 理论上渲染进程卡住**可能连累桌面图标点击**。
WE/Lively 都这么干且能用，但**必须在 PoC 里测一条**：挂上之后拖拽/单击桌面图标，确认不卡顿。

### 2.12 【实测 · 推翻了已定决策】写一次系统壁纸 = 拆掉一次挂载层

**已实测**（`tools/tmp/watch-workerw-cause.py`，125 秒 × 25 次采样）：

| 采样时刻 | Progman 的子 WorkerW | TranscodedWallpaper mtime | 事件 |
|---|---|---|---|
| 16:06:00 | `0x450c10` | 16:05:38 | — |
| 16:06:10 | `0x120910` | 16:06:08 | **WorkerW 重建 + 壁纸写入** |
| 16:06:40 | `0x230952` | 16:06:38 | **WorkerW 重建 + 壁纸写入** |
| 16:07:10 | `0x490988` | 16:07:08 | **WorkerW 重建 + 壁纸写入** |
| 16:07:40 | `0x5f0948` | 16:07:38 | **WorkerW 重建 + 壁纸写入** |

**WorkerW 重建 4 次，壁纸写入 4 次，采样点完全相同（4/4，重合率 100%）。**

⇒ **`0x052C` 造出来的那个 WorkerW，每次系统壁纸写入都会被 Explorer 销毁重建。**

后果：你选的「**双写兜底**」（每换一张图就写一次系统壁纸）会让挂载层**每轮被拆一次** —— 实测写入间隔 **30 秒**（你自己的 `interval=40` + 两块屏各一路）。
若不处理，用户看到的现象是：**桌面每 30 秒闪一下**。

> ⚠️ 附带一个测量教训：用 `SPI_GETDESKWALLPAPER` 判断「壁纸有没有变」是**无效**的 ——
> 应用写的是固定的 `TranscodedWallpaper`，路径永远不变，会得出"壁纸一次都没变"的假结论。
> 判断真实写入必须看 **`TranscodedWallpaper` 的 mtime**。

### 2.13 【实测推出 · 更优挂载点】挂 Progman，**不要**挂 WorkerW

同一批采样里还有两个对照组，**句柄全程一次都没变**：

| 窗口 | 句柄 | 125 秒内变化 |
|---|---|---|
| `Progman`（顶层） | `0x3013a` | **从未变** |
| `SHELLDLL_DefView`（图标层） | `0x1014e` | **从未变** |
| 子 `WorkerW`（挂载层） | 4 次采样全不同 | **每 30 秒换一个** |

而 Progman 的子窗口实测 Z 序是：

```
Progman 0x3013a (5440x2560, WS_POPUP, 可见)
  [0] SHELLDLL_DefView  5440x2560  WS_CHILD|WS_VISIBLE|EX_LAYERED   ← 图标层（Z 序在上）
        └─ SysListView32  5440x2560
  [1] WorkerW           5440x2560  WS_CHILD|WS_VISIBLE               ← 挂载层（Z 序在下）
```

⇒ **首选挂载方案：`SetParent(ourHwnd, Progman)` + `SetWindowPos(ourHwnd, SHELLDLL_DefView, …)`
把自己插到图标层之后（更下层）。**

| 好处 | 说明 |
|---|---|
| ① 不受壁纸写入影响 | Progman / DefView 句柄稳定 ⇒ **「双写兜底」重新变得可行，你的原决策不用改** |
| ② **根本不需要发 `0x052C`** | 少一整步原生调用和它的失败分支 |
| ③ 看门狗简化 | 只需周期性**重申 Z 序**（`SetWindowPos`），不需要重挂；孤儿风险大幅下降 |

**未实测（阶段 0 第一件事）**：Progman 会不会重绘盖住我们？需不需要周期性重申 Z 序？
**退路**：Progman 方案失败 ⇒ 回到 WorkerW 方案，**且必须同时取消双写兜底**（或降级为「只在启动/退出时写一次」）。

### 2.14 【阶段 0 实测 · **修正了 §2.13 的乐观结论**】Progman 句柄稳定 ≠ 子窗口 Z 序稳定

阶段 0 PoC（`tools/probe-attach.js`，**24 项断言全绿**）实测：

| 验证项 | 结果 |
|---|---|
| `SetParent` 到 Progman 后 Chromium 是否继续出帧（**唯一的风险闸门**） | ✅ **继续出帧**。挂载后洋红占比 **1.0**，两帧像素差异 **44.6%**，渲染进程帧计数 +367 |
| 桌面图标是否仍在我们之上 | ✅ `SHELLDLL_DefView` 在 index 0、我们在它之后 |
| Alt+Tab / 焦点 | ✅ 没抢焦点（前后前台句柄相同）、补了 `WS_EX_TOOLWINDOW` |
| 卸载是否干净 | ✅ 退出后 Progman 下无残留 |

**但发现一个 §2.13 没预料到的现象**：
**每写一次系统壁纸，Explorer 会在 Progman 下新建一个 WorkerW 并插到 `SHELLDLL_DefView` 之后
⇒ 我们的窗口被挤到下一层、被完全盖住**（画面占比 1.0 → 0）。

写入后的真实 Z 序（实测打印）：

```
[0] SHELLDLL_DefView   0x1014e   ← 图标层
[1] WorkerW            0x711ac   ← Explorer 新建的，盖住了我们
[2] Chrome_WidgetWin_1 0x30032c  ← 我们的窗口，被压到下面
```

⚠️ **最容易误判的一点**：此时 `assertMount()` 依然报 `attached: true`、`actualParent = Progman` ——
父子关系确实**没变**。所以「挂载是否还活着」**不能只看父子关系**，必须看 Z 序。

⇒ 看门狗判据定为 **`isZOrderIntact(hwnd, anchor)`**：

```js
GetWindow(hwnd, GW_HWNDPREV) === anchorHwnd   // 紧贴我上面的必须就是 SHELLDLL_DefView
```

**补救通道已验证有效**：`SetWindowPos(our, DefView, …)` 重申**一次**即恢复（实测第 1 次重申后 0.6s 内画面回来），
恢复后 1.3s 内没再被挤下去。连写 5 次壁纸后重申一次同样能恢复。

### 2.15 【阶段 0 实测】WorkerW 不会无限堆积

连写 5 次系统壁纸，Progman 下的子 WorkerW 数量：

```
起始 1 → 第1次写后 4 → 4 → 4 → 4 → 4
```

第 1 次跳到 4 之后**稳定不再增长**；探针进程退出后回到 1（Explorer 自己清理）。
⇒ 长跑不必担心句柄泄漏，但要**预期最多有 3 个 WorkerW 压在我们上面**（看门狗要能穿透它们）。

### 2.16 【阶段 0 实测 · **需要重新拍板的设计点**】双写兜底会让画面每轮消失约 1 秒

把 §2.12 + §2.14 摞在一起就是：

- 你应用现在的节奏是**每 40 秒写一次系统壁纸**（`interval=40` × 两块屏各一路 ⇒ 实测约 30 秒一次）
- 每次写入 ⇒ Explorer 重建 WorkerW ⇒ **我们的画面被盖住**
- 看门狗重申一次能救回来，但期间有 **0.6~1 秒**屏幕上是系统壁纸

⇒ 观感是**桌面每 30 秒闪一下**。这与原决策「双写兜底（每换一张图就写一次系统壁纸）」直接冲突。

**三个可选口径**（需要你选，见 §5 第 5 条）：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. 动态模式下降频写**（推荐） | 动态桌面开着时，系统壁纸只在**启动 / 停止 / 换相簿**时写一次，不再每换图都写 | 兜底仍在（退出/崩溃后桌面是最近一张），但不保证「退出瞬间那张」是最新的 |
| B. 保持每轮写 | 照旧每换图写一次，靠看门狗救 | 桌面每 30 秒闪 1 秒 |
| C. 动态模式不写系统壁纸 | 彻底不写（就是你说的「不走系统设置壁纸」） | 锁屏 / 退出后是你自己原来的壁纸 |

## 4. 开发环境隔离（**开工前必须先做**，这是最大的破坏风险）

**风险**：`launchAtLogin = True` 且开机自启**跑的是源码目录** ⇒ 我改源码，用户下次开机就吃到；而用户的应用**此刻正在运行**（pid 13368）。

**方案**：`git worktree` 独立工作目录 + `node_modules` 目录联接复用（**不额外占几百 MB 磁盘**）

```
git worktree add "D:/workbuddy/2026-09-10-17-57-11/electron-wallpaper-live" -b feature/live-desktop
# 在该目录里用目录联接复用依赖，避免第二次 npm i
cmd //c mklink /J "<worktree>\node_modules" "<原目录>\node_modules"
```

- 原目录**留在 master**，用户的自启与正在跑的实例**完全不受影响**
- 我所有实验都在 worktree 里，profile 一律 `--user-data-dir` 隔离
- 收尾关实例**按 PID 树后序**；**禁止** `proc-list.py --kill --under=<项目目录>`（会连用户的实例一起关）
